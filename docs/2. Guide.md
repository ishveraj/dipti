## CPT UI Caching, Sitemap & Settings
### Caching
When Page or CPT is saved, CMS generates a special cache and stores in DB for page load speed, however sometimes cache generation for some CPTs may **NOT** be required (Transactions or sensitive data related CPTs).
1. Set ACF > Post Types > Advanced Configuration > REST API > `Show in REST API` to **False** to ensure CPT does **NOT** generate cache files 

### Sitemap XML
Sitemap URL lists all CPTs, however sometimes some CPTs are **NOT** required to be listed in sitemap XML (Transactions or sensitive data related CPTs).
1. Set ACF > Post Types > Advanced Configuration > URLs > `Publicly Queryable` to **False** to ensure CPT does **NOT** appear on Sitemap URL

### Author setting in CMS
When creating CPTs, Supports > Author will determine if the CPT will display Author columns & allow CMS user to change Author of a CPT data (Only if ACF does not hide the author in the first place).
1. Tick checkbox ACF > Post Types > Advanced Configuration > General > Supports > `Author` to ensure CPT displays Author columns & allows feature for CMS user to change Author

## Multi Language Support (Polylang)
To configure for multi language support, the following steps can be taken
1. Ensure `Polylang` Wordpress plugin is installed AND configured in CMS before configuring the following
1. `.env` set `LANGUAGE_SUPPORT` to multiple
1. Add a tag wherever you wish that is used to change the language of the site AND apply its ID or class in `src/utils/CMS/Routing/ > PolyLangSwitcher > el` parameter

## CSP & CORS
CSP and CORS errors occurs when servers are not whitelisted correctly. CSP prevents scripts from different domains from running in the app. CORS prevents different domains from sending request to the app's backend. 
Take note of the following to ensure to find the right places to whitelist.
1. For CSP whitelist in **index.jsx**.
1. For CORS whitelist in **.env**.

## REST APIs
To create REST API endpoints we can use /public/backend/REST to create folders and PHP classes. The following patterns can be met to create endpoints:

File at `backend/REST/DashboardExample/ProfilePage/class-settings.php`
```
namespace REST\DashboardExample\ProfilePage;

class Settings {
   public static function private_get_list_settings(){
     // some awesome code
   }

   public static function private_post_update_settings(){
     // another awesome code
   }

   public static function public_get_list_profiles(){
     // more awesome code
   }

   public static function public_post_register(){
     // more awesome code
   }
}
```

The above parameters follow these naming rules:
- `\DashboardExample\ProfilePage` uses **UpperCamelCase** where each word in the identifier begins with uppercase letter with no underscores or other separators between the words
- `Settings` - uses **UpperCamelCase**
- `private_get_list_settings()` uses **snake_case** where all letters are lowercase and only allowed to use `public` or `private` followed by underscore and `get` or `post`

With this names used, the endpoint when making request can be written as:
### GET
```
https://example.com/hub/api/get/public/dashboard-example/profile-page/settings/list-settings
```
### POST
```
https://example.com/hub/api/post/public/dashboard-example/profile-page/settings/list-settings
```
### NSJ useAPI
```
useAPI('public/dashboard-example/profile-page/settings/list-settings');
```
where all letters are lowercase and underscores are converted into `-`

## Coding Standards

### General
- Avoid using var. Use `const` or `let` instead.
- Component names MUST be `UpperCamelCase`
- Variables and Function names MUST be `camelCase`
- Any `console.logs` for tests MUST be removed before moving to production
- Comments inside `return <></>` MUST be removed
- Avoid using inline `() => {}` inside `return <></>`

### JS events
- Any events added inside export MUST be removed via `onCleanup()`

### PDFs
- Iframe PDFs must be loaded via PDF JS
- Sensitive PDFs must be loaded via useAPI return PDF function

### ACF
- A **main parent field type group** is used containing the name of the page/cpt it is attached to. All other fields will go under this main parent field. Naming convention examples are as follow:-
  - Fields to be attached to the Home page will be named as **page_home**
  - Fields to be attached to CPT Blogs will be named as **cpt_blogs**

This naming convention strictly ensures that all fields will have a unique name which further prevents database data collisions.
